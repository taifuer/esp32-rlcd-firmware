# v0.31.0 AI 对话迁移与体验完善

2026-09-28，用户在 `0.31.0-dev.2` 中完成新模型授权，确认 AI 对话恢复正常并同意发布
v0.31.0。正式版沿用该候选的功能源码。以下保留实施、排查与发布记录；本轮未通过 USB
写入固件。

## 范围

- 默认且唯一可选模型改为 `qwen-audio-3.0-realtime-flash`。旧 Omni 编号只保留用于读取
  已发布配置，不能用于新表单、连接地址或会话协议。迁移原因和官方资料见
  [模型评估](cloud-voice-evaluation.md#2026-09-28旧模型下线与-v0310-迁移)。
- 从双槽最新有效配置迁移，保留 API Key、Host、开关，向另一槽提交；保留旧槽，
  不在解码时提前改写模型而影响槽选择。未知格式和校验损坏的记录不作为有效配置。
- 迁移失败时原凭据仍保留，本次使用 RAM 中的新模型，门户提示重新保存；不阻断本地
  功能，也不偷偷继续请求旧模型。成功说明只在本次开机显示；下次读取新模型不再迁移。
- 采用严格错误码分类：身份验证、访问权限、模型、限流、超时、网络、安全连接、服务、
  连接关闭、设备资源和未知。原始错误正文不进入界面；404 不能直接证明模型下线，未知失败不推断
  欠费。失败后不自动重发音频或换地域。
- 门户显示当前模型、迁移结果、最近会话结果。最近结果只保存在 RAM，绑定配置代次；
  保存或清除后不沿用此前的成功，重启后尚未测试。成功需至少完整结束一轮本地播放；
  后续轮次失败显示失败，取消与闹钟抢占不误报服务故障。
- 不增加网络探测按钮或开机收费测试。设备仍由用户长按发起，使用五轮半双工，
  30 秒续问和五分钟新轮准入；保留简短回答提示与按播放进度推进的四行字幕。
- Audio 3 只发送其已核对的参数；`max_history_turns` 不是输出字数上限，不发送旧模型
  专属 `max_tokens` 或 `qwen3-asr-flash-realtime`。不改变缓冲容量和资源所有权。

## 不纳入

唤醒词、后台监听、自动 VAD、全双工、无限轮次、跨会话历史、云端指令执行、其他服务商、
新设备菜单、音乐上传队列恢复和功耗策略变更不在本轮。分区和离线模型保持兼容。

## dev.1 实机连接问题（2026-09-28）

用户确认门户显示新模型及迁移完成，但 AI Chat 一直显示 CONNECTING，最后提示等待
响应超时。Windows COM5 过滤采集到以下关键过程（时间为启动后毫秒）：

```text
873957  online network session acquired
873966  websocket_client: Started
875645  websocket_client: Did not get TCP close within expected delay
888973  websocket_client: Client was not started（两次）
889002  online network session released; station kept
889003  cloud conversation failed: ESP_ERR_TIMEOUT
```

- 设备运行 `0.31.0-dev.1`，Wi-Fi 已连接，未观察到 panic 或恢复模式；门户模型迁移已
  完成。市场页能加载，不能把 AI Chat 的失败笼统归为整个网络不可用。
- 上游该关闭警告仅出现在 WebSocket 关闭握手分支。结合此时尚未进入本地清理、
  dev.1 代码忽略 `WEBSOCKET_EVENT_CLOSED` / `FINISH`，确认连接已经结束，但上层仍然
  等待就绪，约 15 秒后把它报成响应超时。不是一直卡在清理或网络锁未释放。
- **当时尚未查明服务端关闭会话的原因。** dev.1 的 INFO 日志不包含此路径的关闭码，不能
  据此断言 Key 无效、模型不可用或 `session.update` 参数错误。后续定位见下文
  “dev.2 实机恢复与发布确认”。
- 据此确定 dev.2 需要处理非预期 CLOSED/FINISH，保留已存在的明确错误和主动取消语义，并补充
  不包含凭据、正文或音频的连接阶段与数值关闭码诊断；验证后再准备 Beta 候选。
  当时仅诊断，没有修改或写入新的设备固件，不能把 dev.1 标为实机验证通过。

串口只发送 `GET_BOOT` / `GET_NETWORK`，云请求由用户按键触发。采集使用完整消息
白名单，不保存原始流：上游存在 ERROR 级别输出 Upgrade 请求头的路径，不能直接回显
原始日志或开启 DEBUG。首次打开原生 USB 口触发过一次 USB 复位，后续重新打开未复位。

## dev.2 修复与 Beta OTA（2026-09-28）

用户确认后修复关闭状态处理；准备该候选时，服务端关闭原因仍待新诊断确认，未将构建
成功记为云端对话恢复。请求 JSON、发送顺序、Key、Host、NVS 格式和多轮规则均不变。
后续定位与用户反馈见下文“dev.2 实机恢复与发布确认”。

- 非预期 CLOSED、FINISH、DISCONNECTED 和协议 `session.finished` 立即进入失败清理；
  保留首个具体错误。主动取消、正常结束、闹钟抢占不被后续回调误报为故障。
- 迟到连接、会话、音频事件不重新激活已结束会话；重复创建/确认事件不回退正在监听
  或收音的状态。发送返回前收到确认或关闭事件时，也不覆盖较新的状态。
- 增加 RAM 初始化里程碑与首个有效关闭码。门户失败结果可展开“连接诊断”，USB
  `GET_CHAT` 可读取同一摘要；配置变更和重启不沿用旧结果，不保存正文或服务端关闭原文。
- 固定采集脚本与 UAC/COM 恢复流程已保存到开发、烧录文档。`tcp_transport` 的潜在认证
  请求头日志在编译期禁用；构建脚本检查危险日志格式未进入对象文件，独立检查也确认对象
  和静态库没有 `esp_log` 引用，不只依赖 INFO 上限或运行时过滤。
- 实机旧日志曾记录主线程历史栈水位仅余 108 字节。主线程独占的对话显示快照改为静态

  减少 1136 字节。`GET_CHAT` 报告在 PSRAM 分配，失败时只报不可用，不增加大栈对象。
  这些是构建检查结果，更新后的真实栈水位仍需复测。
